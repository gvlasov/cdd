Concept-Driven Design

A software engineering method for organizing code by meaning

Concept-Driven Design, or CDD, treats a codebase as a reflection of the reality a system is about. It asks engineers to place files by the concepts, stakeholders, processes, and platform concerns they express, instead of scattering them by framework convention or file type.

The Problem CDD Addresses

Most software projects are arranged for tools. Backend files go under one tree, frontend files under another, tests under a third, migrations somewhere else, and documentation wherever a team happened to put it. That structure is convenient for compilers, test runners, bundlers, and frameworks, but it is not how engineers understand a system.

Engineers usually think in questions like: What is an order? How does billing work? Where does the user profile appear? What changes when a subscription is cancelled? In a tool-driven project, answering one conceptual question requires visiting many technical-role directories.

CDD begins from the opposite assumption: related by meaning means kept together; unrelated by meaning means separated, even when a framework would normally group the files together.

This matters because scattered meaning creates shotgun surgery. A single change to one idea can require edits across models, controllers, routes, views, tests, fixtures, migrations, API schemas, assets, and documentation. The cost is not only typing. The real cost is attention spent reconstructing the concept from pieces.

The Core Idea

CDD organizes a project around the concepts of its problem domain. A concept is a cohesion unit: a group of representations held together by meaning. A file belongs to the concept whose meaning it expresses, not to the runtime mechanism that happens to execute it.

In CDD, a project is a source-code reflection of a conceptual system. That project contains concept reflections, stakeholder concerns, processes, platform support, and developer commands. The filesystem becomes a map of the software's meaning.

What changes

Instead of asking "Is this a controller, model, component, or test?" you ask "What is this file about?"

What stays practical

Frameworks, build tools, Docker, package managers, and test runners still exist. CDD places their generic setup in platform and places domain-specific reflections with their concepts.

The Essential Vocabulary

Concept

A concept is the identity of a cohesive set of reflections. It is not one class, table, component, or document. Those are reflections of the concept. For example, an order concept may include an entity, repository, view, controller, import command, database migration, tests, fixtures, and written explanation.

Reflection

A reflection is a way for a concept to exist in the project. A ProductDTO, ProductView, product table migration, product screenshot, product import script, and product documentation can all be reflections of products. There is no single canonical reflection apart from the concept name.

Cohesion

Cohesion is the principle that things related by meaning should stay together. CDD applies it at every scale: expressions inside a statement, statements inside a function, functions inside a module, files inside a directory, and directories inside a project.

Stakeholder

A stakeholder is a person or group concerned with the project: users, owners, developers, regulators, operators, customers, or a narrower group specific to the product. Stakeholder directories hold goals, constraints, research, support materials, and other representations about that stakeholder.

Process

A process is an ordered change in state over time. A checkout flow, data import, onboarding journey, moderation workflow, deployment routine, or discovery practice can be represented as a process when the important thing is how state changes and why.

Platform

Platform contains the generic means that run, build, check, and deliver the project: framework entrypoints, Docker setup, package manager configuration, build tools, test runners, deployment wiring, editor integrations, and other infrastructure.

The CDD Project Shape

The usual top-level structure separates meaning from mechanism. A project does not need to start perfectly, but these directories give engineers a stable first question for every file: is this about a concept, a stakeholder, a process, a platform concern, or a developer command? 

/concepts/
  orders/
    Order.php
    OrderRepository.php
    OrderController.php
    OrderView.vue
    CreateOrdersTable.php
    SettleOrders.php
    Order.md

/stakeholders/
  customers/
  support-agents/
  developers/

/processes/
  checkout/
  onboarding/
  refunds/

/platform/
  docker/
  frontend/
  databases/
  testing/

/commands/
  build
  test
  deploy
  mysql

/sandbox/
  experiments that have not found their proper home yet

The exact names depend on the project, but the separation is the important part. Concepts are for the domain. Stakeholders are for concerned people and groups. Processes are for ordered changes over time. Platform is for runtime and tooling support. Commands are the developer shell surface.

Placement Rules for Engineers

Situation CDD move
A file is about a domain thing, such as orders, users, products, accounts, messages, or subscriptions. Put it in that concept directory, regardless of whether it is a model, test, controller, view, migration, fixture, or command.
A file configures a generic tool, framework, runtime, package manager, compiler, test runner, or deployment mechanism. Put it under /platform with the platform concern it belongs to.
A file describes a person, role, group, expectation, need, constraint, or research subject. Put it under /stakeholders.
A file describes or implements a workflow, lifecycle, sequence, state transition, or repeated activity. Put it under /processes.
A script exists so developers can operate the project easily. Expose it through /commands. Prefer a symlink to an implementation placed with the concept, process, stakeholder, or platform concern it represents.
You cannot yet tell what the thing is about. Use /sandbox temporarily, then move it once the concept, process, stakeholder, or platform concern becomes clear.

A useful test is whether the placement can be explained without naming the file extension or framework. "This belongs to orders because it defines how orders are displayed" is a CDD explanation. "This belongs in views because it is a Vue file" is a tool-driven explanation.

Project Shell Commands

The command shell is one of CDD's most practical selling points. A CDD project should feel like it comes with its own command language. Developers should not need to memorize long tool invocations, inspect Docker files, remember package-manager details, or search documentation before they can operate the project.

Whenever a repeated shell action becomes part of working on the project, give it a boring, discoverable command name.

The standard entrypoint is cdd. With no arguments, or with self-help, it lists the built-in CDD commands: 

$ cdd
cdd self-help  - show cdd subcommands
cdd help       - show available project commands
cdd init       - initialize a CDD project directory
cdd print      - print indexed project code
cdd self-upgrade - self-upgrade CDD support from CDD_SOURCE_PATH

cdd help is the project-level discovery command. It reads executable files from /commands and shows the operations this project exposes: 

$ cdd help
bash:install                    - install CDD support for Bash for current user
claude:install                  - installs CDD methodology as Claude Code skill
codex:install                   - installs CDD methodology as Codex skill
codex:project-terminal:install  - installs the CDD Codex project terminal launcher
fish:install                    - install CDD support for Fish shell for current user
jetbrains:plugin:build          - build the JetBrains CDD integration plugin
reason                          - start a Codex session for interactive reasoning
refine                          - copy methodology text for LLM refinement
self-upgrade                    - self-upgrade CDD support
tests                           - run project tests in Docker

The important design choice is that command names describe the developer's goal, not the underlying tool. A project can change from Docker Compose to another runner, from npm to pnpm, or from one test harness to another while keeping stable commands such as up, test, lint, and build.

Daily operation

$ cdd help
$ cdd tests
$ cdd print
$ cdd refine

These commands let an engineer discover, test, inspect, and refine the project without reconstructing tool details first.

Common project vocabulary

$ cdd up
$ cdd build
$ cdd lint
$ cdd test
$ cdd deploy

Not every project has every command, but common operations should use predictable names when they exist.

cdd print as context export

cdd print prints the indexed project files in a readable form. It skips ignored binary-like extensions and symlinks, then prints each file name before its indexed content. This is useful for reviewing the source, passing coherent context to an LLM, or producing a snapshot of what Git currently knows about the project. 

$ cdd print > /tmp/project-context.txt
$ sed -n '1,80p' /tmp/project-context.txt

Commands are entrypoints, not dumping grounds

/commands should usually contain executable entrypoints or symlinks. The implementation still belongs with the concept, process, stakeholder, or platform concern it represents. This keeps commands immediately available while preserving CDD's core placement rule. 

$ ls -l commands/refine commands/codex:install commands/fish:install
commands/refine         -> ../processes/refinement/refine
commands/codex:install  -> ../concepts/agent-skills/install-to-codex
commands/fish:install   -> ../platform/fish/install

This is why shell commands and concept-driven placement support each other. The project gets a simple operational surface, while the source of each command remains near the meaning or tool concern it belongs to.

A CDD Workflow

  1. Observe the reality. Look at users, business language, workflows, documents, policies, data, and constraints. Do not start from framework folders.
  2. Name the concepts. Choose names that engineers and stakeholders can use consistently. Most concepts are plural, such as orders, products, or users. Singleton concepts can be singular when the system has exactly one meaningful instance.
  3. Build reflections. Add the classes, functions, views, tests, migrations, fixtures, assets, docs, and commands that make the concept exist in source code.
  4. Separate platform from meaning. Keep generic tooling in platform. Keep concept-specific behavior with the concept.
  5. Refine as understanding improves. A wrong concept boundary is not failure. It is an observation. Split, merge, or rename concepts when the meaning becomes clearer.

This workflow fits normal engineering. You can still write tests, ship vertical slices, design APIs, use dependency injection, and follow framework constraints. CDD changes where the artifacts live and what mental model governs their boundaries.

Examples in Practice

Order settlement job

A queue job named SettleOrders may look like platform code because a queue worker runs it. CDD places it with /concepts/orders because the job is about orders. The queue worker, queue configuration, and process supervisor belong in platform.

Database migrations

A migration that creates an orders table is a reflection of orders in database state. Its concept-specific definition belongs with orders. The migration runner and database connection setup belong to platform.

Tests

A test for product pricing is a product reflection. A test helper that boots the whole test framework is platform. This keeps tests near the code and language they verify instead of grouping all tests by technical role.

Documentation

Documentation should live with the thing it explains. A product policy belongs with products. A support-agent guide belongs with the support-agent stakeholder. A deployment checklist belongs with the deployment process or platform deployment concern, depending on what it describes.

Adopting CDD in an Existing Project

Retrofitting an old codebase can be expensive, so migration should be deliberate. CDD works best when introduced at a boundary where engineers already need to understand a concept deeply: a new feature, a painful subsystem, or a module being rewritten.

Start narrow

  • Pick one concept that is actively changing.
  • Create a concept directory for new or touched reflections.
  • Move only what you can explain and verify.
  • Expose developer scripts through /commands.

Avoid churn

  • Do not rename the whole project for aesthetics.
  • Do not fight framework autoloading without a reason.
  • Do not hide generic tool setup inside domain concepts.
  • Do not treat /sandbox as permanent storage.

For greenfield work, start with the top-level CDD directories immediately. For legacy work, use CDD first as a thinking tool, then as a placement rule where the payoff exceeds the migration cost.

Benefits and Trade-offs

Benefits

  • Changes to one idea tend to happen in one place.
  • Onboarding starts from domain language, not framework storage rules.
  • Concept directories make useful context boundaries for AI assistants.
  • Documentation, tests, code, and assets reinforce each other because they are colocated by meaning.
  • Framework code becomes easier to identify because generic platform concerns are separated from domain concepts.

Trade-offs

  • Some frameworks assume tool-driven locations, so adapters or configuration may be needed.
  • Teams must learn to argue from meaning instead of habit.
  • Concept boundaries can be wrong at first and require refinement.
  • Legacy migration can cost more than it returns if done mechanically.
  • There is no turnkey universal setup because CDD is a methodology, not one stack-specific framework.

The point is not to make every repository look identical. The point is to make every repository honestly reflect the conceptual system it implements. CDD gives engineers a default place for things, a language for discussing boundaries, and a practical standard for keeping meaning visible in source code.

This introduction is written for CDD adepts: software engineers who use Concept-Driven Design as a practical discipline for placing code, documentation, commands, and platform support by the meaning they represent.
